# 이력서 작성 원칙

## -1. 마스터 불릿 원문 유지 원칙 (최우선)
**master.md의 불릿 텍스트("=>" 뒤 문장)는 그대로 복사해서 쓴다. 새로 문장을 만들지 않는다.**
- 허용되는 편집: (a) 문장 앞/뒤를 잘라 길이를 줄이는 것, (b) 여러 불릿을 순서대로 배치하는 것, (c) 두 개의 짧은 불릿을 접속사로만 이어붙이는 것, (d) 문법상 어색한 접속 부분만 다듬는 것.
- 금지: 같은 의미를 다른 단어·다른 문장 구조로 "재작성"하는 것. 예를 들어 master.md에 "빌드 캐시 적용으로 배포 소요 시간 50% 감축"이 있으면 그대로 쓰고, "빌드 캐싱을 통해 배포 시간을 절반으로 줄였습니다" 같은 식으로 바꿔쓰지 않는다.
- 이유: 매 세션마다 같은 사실을 조금씩 다르게 표현하면 (1) 여러 버전 간 일관성이 깨지고, (2) 면접관이 다른 경로로 두 버전을 보면 신뢰도가 떨어지고, (3) master.md 자체가 표현 변형으로 계속 부풀어 유지보수가 어려워진다.
- master.md에 필요한 불릿이 없을 때만 새로 작성하고, 작성한 문장은 반드시 master.md에도 다시 반영해 다음부터는 그 문장을 재사용한다(레퍼런스 신설이지 매번 재창작이 아님).
- 압축이 꼭 필요해서 어쩔 수 없이 문장을 바꿔야 한다면, 바뀐 이유(글자 수 제약 등)를 간단히 밝히고 진행한다.

## -0.5. 불릿 간결화 원칙 — 배경 설명은 Full Story로
master.md의 회사별 불릿은 "행위 + 핵심 결과" 한 문장만 유지한다. 각 회사 섹션 하단에는 `<details>상세 배경(Full Story)</details>` 블록이 있는데, "왜 그랬는지", "누가 먼저 시도했다 실패했는지", "정확한 수치의 근거·각주" 같은 부연 설명은 여기에만 둔다.
- **불릿을 고를 때**: 기본은 짧은 불릿 그대로 쓴다. 면접 예상 질문에 대비하거나 JD가 특히 깊이 있는 서술을 요구할 때만 Full Story에서 필요한 한두 문장을 가져와 붙인다 — 이때도 새로 재작성하지 말고 Full Story의 문장을 그대로 옮긴다.
- **새 불릿을 추가할 때**: 불릿 자체는 짧게 쓰고, 배경·근거·조건부 설명은 Full Story로 보낸다. 불릿에 "왜냐하면", "단," "참고로" 같은 연결어가 두 번 이상 나오면 십중팔구 Full Story로 옮길 내용이 섞여 있다는 신호다.
- 이 구분을 지키지 않으면 불릿 뱅크가 다시 장문화되어 실제 이력서에 그대로 복사했을 때 문장이 길어지는 문제가 재발한다.

## 0. 공고별 작업 프로세스 (2026-10 개편)
**필터 판별 → 베이스 선택 → 순서·볼드 조정 → 빌드.** 이 네 단계가 전부이며 목표 소요는 10분 이내다. 이전의 JD 분석 → HR/CTO Skim → 컨설턴트 전략 → 실제 수정 4단계, 포지셔닝 선택, 불릿 Drop 판단은 폐지했다. 사용자가 명시적으로 요청할 때만 Skim/컨설팅을 수행한다.

### 0-1. 필터 판별 (지원 전)
3가지 신호 중 **2개 이상**이면 지원한다.
1. **업무 동사**: 설계·리딩·주도·구축 (유지보수·개발 참여·협업 중심이면 약함)
2. **팀 상황**: 첫 iOS 채용 / 신규 SDK·신규 앱 / iOS 소수 인원
3. **우대사항 수준**: 모듈화·코드리뷰/멘토링·안정성 지표
- 신호가 애매하면(연차는 "3년 이상"인데 업무는 시니어 성격 등) 지원 전에 채용 담당자에게 시니어 레벨 포지션인지 먼저 확인한다.
- 사례(샵라이브 iOS 7년 이상, 사후 판별): 우대사항에 아키텍처·리팩토링·코드리뷰가 있어 신호 ③ 해당, 주요업무가 SDK 3종 개발이라 팀 상황 ②는 신규 여부가 불명확해 애매, 업무 동사는 "개발" 위주라 ① 약함. 1~2개로 경계선이며 "7년 이상" 연차가 시니어 신호라 인터뷰 가능성을 봤고 실제로 스크리닝까지 갔다. 이런 경계선 공고는 지원 전에 담당자에게 레벨·팀 상황을 확인한다.
- 신호 개수는 지원 표(`application-history/README.md`)에 기록한다. 1개 이하면 지원하지 않는다.
- 연차 요건이 낮고 연봉이 비공개인 공고는 시니어 자리가 아닐 가능성이 높다. 신호 판별의 참고만 하고 그것만으로 배제하지 않는다.

## 1. 사실 정확성 — 인과관계·시점·범위 오류 잡기
문장을 압축하다 보면 원래 서로 다른 두 사실을 하나의 인과관계로 묶어버리는 실수가 잦다. 반드시 원본 사실(master.md)을 다시 확인한다.
- **인과관계 오류**: 서로 무관한 두 성과를 하나의 인과로 묶지 않는다(예: 캐싱과 API 호출 최적화와 길안내 구현은 각각 별개 작업).
- **주체 오류**: 기 구축된 도구(Amplitude 등)를 본인이 "구축"한 것처럼 쓰지 않는다. "활용"과 "직접 구축"은 구분.
- **시점 불일치**: 경력 항목의 날짜 범위와 불릿 내용의 실제 시점이 다르면 오해를 유발한다 → 날짜 제약이 있는 섹션에는 그 시기에 실제로 있었던 내용만, 최근 활동은 날짜가 없는 섹션(외부활동 등)으로 분리.
- **적용 범위 과장**: 실제로는 특정 프로젝트 하나에만 적용된 것을 전체에 적용한 것처럼 쓰지 않는다. 범위가 다른 두 사실을 한 문장에 묶을 땐 범위를 각각 명시.
- 수치/사실이 master.md와 충돌하면 임의로 판단하지 말고 사용자에게 확인 질문을 먼저 한다.
- **성과가 아닌데 JD 키워드에 맞추려고 지어내지 않는다**: 실제로 한 일 중에서 JD와 관련된 걸 고르는 것(선택·배치)은 정상이지만, 안 한 일이나 스치듯 해본 것을 JD 키워드 때문에 성과처럼 포장하지 않는다. "이 불릿이 실제로 있었던 일인가"가 항상 "JD 언어로 어떻게 표현할까"보다 먼저다.

## 2. 문장 압축 원칙 — "한 일 나열"이 아니라 "결과·임팩트" 중심
> 이 원칙은 master.md에 불릿을 **새로 쓸 때**만 적용한다. 공고별 작업에서는 기존 불릿을 다시 쓰지 않는다(-1번 원칙, 0-3번).
- 행위만 적은 불릿("~을 개발했습니다", "~을 도입했습니다")보다 결과·수치·임팩트가 붙은 불릿을 우선한다(예: "Fastlane으로 통합" → "Fastlane으로 통합해 배포 시간 50% 감축").
- **행위로 끝나는 불릿은 결과/임팩트 절을 붙여서 마무리한다.** "~을 구현했다"로 끝내지 말고 "~을 구현해 [수치/효과]를 얻었다"로 끝낸다. 단, 지어낸 효과가 아니라 실제 있었던 결과여야 한다 — 없으면 억지로 만들지 말고 다음 우선순위(행위 자체의 기술적 난이도·범위)로 대체한다.
- 필러 표현 제거: "직접", "재직 중"(맥락상 암시되면 생략), "선제적으로 담당 부서에" 같은 늘어지는 수식어부터 줄인다.
- 같은 어근 반복 금지: 같은 개념이 한 문장에 두 번 등장하면 하나로 합친다.
- 수치 표현은 정확한 인과로: "API 호출 절감"과 "데이터 사용량 절감"은 다른 말이니 실제 근거에 맞는 쪽을 쓴다.
- 회사 경력 압축 시 개인 프로젝트보다 우선순위가 높다 — 개인 프로젝트는 오너십/이니셔티브를 보여주는 핵심 수치만 남기고 나머지는 압축.
- 소개문은 문단(서술형), 경력은 불릿형이 기본 — 스캔 속도·비교 용이성·ATS 친화성 때문에 경력 불릿이 유리하다. 복잡한 인과관계를 풀어야 하는 스토리텔링은 이력서보다 포트폴리오/면접에서 다루는 쪽이 낫다.

## 4. 스킬 태그 관리
- **본문-태그 정합성 원칙**: 섹션 본문에 서술이 없는 스킬 태그는 원칙적으로 정리 대상.
- **예외 1 (의도적 태그 전용)**: 미출시/비공개 개인 프로젝트 경험(TCA 등)은 "본문에는 기재하지 않고 스킬 태그로만 노출"하는 것이 의도된 설계일 수 있다.
- **예외 2 (JD 필수 스택)**: JD가 명시한 기술인데 압축 과정에서 본문 근거가 사라졌다면, 태그만 남기기보다 가장 impact 있는 실제 경험을 본문에 복원하는 걸 우선 검토. 복원이 안 되면 그때 태그 삭제 여부를 사용자에게 확인.
- 태그 정리/추가는 매번 섹션별 태그 줄과 master.md 스킬 마스터 리스트 둘 다 동기화.

## 5. 포지셔닝 (폐지 → 베이스 ①②)
이전의 포지셔닝 A~G 선택은 폐지했고 master.md 섹션 0-1의 베이스 ①②로 통합했다. 섹션 1의 A~G 소개문은 문장 재료 참고용이다.
- **쓰지 않는다**: 회사별 클로징 문장(도메인 도전형·미션 공감형·제품경험 공감형), 포부형 마무리, 과스펙을 숨기려고 경력 요약 줄을 공고마다 바꾸는 방식, AI 활용 경험 섹션을 위로 올리는 구조 옵션.
- 경력 요약 줄은 두 베이스 공통 한 줄로 고정한다(모바일 8년+, Mobile Tech Lead 노출; 총 경력 숫자는 쓰지 않음). 시니어 톤을 낮추지 않는다.
- iOS 5년+는 숨기지 않고 요약 줄에 병기한다. "iOS 9년+"는 사실 오류이므로 금지.

## 8. PDF 렌더링 워크플로우 (줄바꿈 QA · 레이아웃 고정 템플릿 기준)
> 레이아웃은 템플릿 고정. 평소에는 0-4의 3가지 확인만 한다. 아래는 줄바꿈 이상이 실제로 발견됐을 때만 참고.
- `word-break: keep-all`을 적용해도 weasyprint에서는 특정 폭에서 한글 단어가 음절 단위로 쪼개지는 경우가 있다(완벽하지 않음).
- 불릿 재작성이 금지이므로 문장을 줄이는 대신 해당 불릿 제거 또는 순서 이동으로 해결한다.
- 문장을 줄여도 1줄에 안 들어가면 2줄이 되는데, 줄이 꺾이는 지점에서 단어가 쪼개지지 않는지 반드시 이미지(`pdftoppm`)로 변환해 육안 검수한다.
- 쪼개짐 발견 시: ① 문장을 더 줄여 1줄로 만들거나, ② 위험 단어에 `<span style="white-space:nowrap">`을 개별 적용.
- 문장을 줄이면 새로운 단어가 그 자리로 이동해 다시 쪼개질 수 있으므로 수정 후 재검수는 매번 필수.
- 업로드된 양식(PDF)을 재현할 때: `pdftoppm`으로 이미지 변환해 시각 스타일 파악 → 동일 스타일 HTML+CSS 작성(Noto Sans CJK KR 등 한글 폰트 명시) → weasyprint 변환 → 페이지 이미지 재변환으로 분량·줄바꿈·여백 검수 → 마크다운 원본과 PDF 소스(HTML) 두 곳에 항상 동일한 문구 반영.

## 9. master.md 유지보수 규칙
새 이력서 버전이 업로드될 때마다(베이스 ①②에 영향을 주는 변경은 반드시 사용자 확인 후 반영) 자동으로 스캔해서 신규 패턴(소개문 구조, 새 불릿, 새 스킬 태그, 새 수치, 새 링크 등)을 master.md에 반영한다. 단, 기존 master.md와 수치·사실이 충돌하면 임의 반영하지 말고 사용자에게 확인 질문을 먼저 한다.
